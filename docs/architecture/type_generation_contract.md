# Type Generation Contract

## 1. Schema & Type Contract Philosophy
The PostgreSQL schema is the single, absolute source of truth for the Plinth application. 
TypeScript types generated by Supabase (`src/types/supabase.ts`) serve as the mandatory architectural contract between the database layer and the application layer. Hand-written approximations or manual schema mirrors are strictly forbidden.

## 2. Migration & Type Regeneration Discipline
Whenever a migration is applied that alters the `public` schema in any way (tables, columns, functions, views, or enums), the TypeScript types must be immediately regenerated.
If the local Docker environment is unavailable or out of sync, types must be pulled directly from the live hosted project to ensure strict parity.

**Approved Regeneration Command:**
```bash
npx supabase gen types typescript --project-id csncpvjlgbwxhjfarcnp > src/types/supabase.ts
```

## 3. Forbidden Typing Patterns
The following patterns are strictly prohibited in the codebase to prevent schema-contract integrity issues:
- **`any` casting on database clients:** Casting the Supabase client (e.g., `(db as any)`) to bypass type-checking is strictly forbidden. 
- **Manual Table Declarations:** Do not define `export interface TableX { ... }` manually if the table exists in Supabase. Always import from `Database['public']['Tables']`.
- **Implicit `any` bypasses:** Do not use `// @ts-ignore` or `// @ts-expect-error` to force queries through the compiler.

## 4. Intelligence Typing Integrity Rules
The intelligence services (e.g., `src/lib/services/intelligence.ts`) rely on highly specific operational schemas and analytical views. 
- These services must only consume fully typed operational entities as derived from `src/types/supabase.ts`.
- When querying SQL Views (e.g., `vw_job_financial_burn`), the view must be present in the generated types. If it is not, the type file must be regenerated rather than bypassed.

## 5. Operational Schema Governance Rules
All operational joins and aggregations must rely on foreign key constraints explicitly mapped in the generated types. 
- If a query requires a join (e.g., `deliverables(job_id)`), the foreign key must exist in Supabase and be reflected in the TypeScript type map.
- DTOs (Data Transfer Objects) must use Zod to validate incoming runtime payloads, but their output types (`z.infer`) must align with the generated Supabase `Insert` or `Update` types before interacting with the database.
